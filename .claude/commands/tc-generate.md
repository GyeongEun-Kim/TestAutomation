너는 QA 엔지니어야. 기획서를 분석하여 테스트케이스를 설계하고 Notion 데이터베이스에 등록하는 작업을 수행해.

> TC 설계 규칙, 다양성 요건, 어서션 기준 상세 → [spec.md](../../spec.md)

---

## 1단계 — 사전 확인

`.env`를 읽어 `NOTION_PARENT_PAGE_ID`, `PROJECT_NAME`이 올바르게 설정되었는지 확인해.
미입력이면 사용자에게 알리고 중단해.

---

## 2단계 — 기존 데이터 초기화

새 기획서 분석 시작 전에 이전 프로젝트 데이터를 모두 정리해:

1. `.notion-db-id` 파일 삭제
2. `docs/{PROJECT_NAME}.md` 파일 삭제
3. `tests/{PROJECT_NAME}/` 하위 파일 모두 삭제
4. `pages/{PROJECT_NAME}/` 하위 파일 모두 삭제
5. 완료 후 사용자에게 알림

---

## 3단계 — 기획서 분석

`plans/` 내 PDF 파일과 `docs/` 내 마크다운 파일을 읽어 기능 목록, 비즈니스 로직, 순서도를 파악해.
파일이 없으면 사용자에게 요청하고 중단해.

분석 결과를 `docs/{PROJECT_NAME}.md`에 저장해.

---

## 4단계 — TC 설계 (Given-When-Then 구조)

분석 결과를 바탕으로 TC 목록을 설계해.

### TC 필드

| 필드 | 설명 |
|---|---|
| 케이스ID | `C-01` 형식 고유 ID (전체 일련번호) |
| 기능 | 테스트 대상 기능명 |
| 구분 | 정상 / 예외 |
| Given | 전제 조건 (구체적으로) |
| When | 사용자 동작 및 입력값 |
| Then | 기대 결과 (모호한 표현 금지) |
| 우선순위 | High / Medium / Low |

### 설계 규칙

[spec.md](../../spec.md)의 **TC 다양성 필수 요건**과 **기능 유형별 최소 TC 수**를 반드시 준수할 것:

- **진입점 다양성**: 동일 기능이 복수 화면에서 동작하면 각각 TC 분리
- **필터/검색 조합**: 단일·복합·초기화·빈결과 포함 (최소 8개)
- **인증/권한 다양성**: 로그인 방식·역할별 TC 분리
- **상태 전환 쌍(Pair)**: 양방향 전환 + 새로고침 후 영속성 검증
- **경계값 및 예외 입력**: 빈값, 최대 길이 초과, 특수문자

[spec.md](../../spec.md)의 **어서션 품질 기준** 금지 패턴도 TC 설계 단계에서 반영할 것.

---

## 5단계 — TC 확인 요청

설계한 TC 목록을 표 형태로 사용자에게 보여주고 확인을 받아.
수정 요청이 있으면 반영해.

---

## 6단계 — Notion DB 생성

`notion-create-database` 도구로 DB를 생성해:

- parent: `.env`의 `NOTION_PARENT_PAGE_ID`
- title: `[{PROJECT_NAME}] TC 관리`
- properties: [spec.md](../../spec.md)의 **Notion DB 스키마** 기준

생성된 DB ID를 `.notion-db-id` 파일에 저장해.

---

## 7단계 — TC 업로드

`notion-create-pages` 도구로 TC를 DB에 등록해.
API 안정성을 위해 한 번에 **최대 10개씩 배치 처리**해.

---

## 8단계 — 완료 보고

업로드된 총 TC 수와 Notion DB 링크를 사용자에게 보고해.
