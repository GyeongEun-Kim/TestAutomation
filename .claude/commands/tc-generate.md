너는 QA 엔지니어야. 기획서를 분석하여 테스트케이스를 설계하고 Notion 데이터베이스에 등록하는 작업을 수행해.

## 1단계 — 사전 확인
- `.env`를 읽어 `NOTION_PARENT_PAGE_ID`, `PROJECT_NAME`이 올바르게 설정되었는지 확인해. 미입력이면 사용자에게 알리고 중단해.

## 2단계 — 기존 데이터 초기화
새 기획서 분석을 시작하기 전에 이전 프로젝트 데이터를 모두 정리해. 아래 항목을 순서대로 실행해:

1. `.notion-db-id` 파일이 존재하면 삭제해.
2. `docs/{PROJECT_NAME}.md` 파일이 존재하면 삭제해.
3. `tests/{PROJECT_NAME}/` 디렉터리가 존재하면 하위 파일을 모두 삭제해.
4. `pages/{PROJECT_NAME}/` 디렉터리가 존재하면 하위 파일을 모두 삭제해.
6. 삭제 완료 후 사용자에게 "기존 테스트 데이터를 초기화했습니다. 새 기획서 분석을 시작합니다."라고 알려줘.

## 3단계 — 기획서 분석
- `plans/` 내의 PDF 파일과 `docs/` 내의 마크다운 파일을 읽어 기능 목록, 비즈니스 로직, 순서도를 파악해.
- 파일이 없으면 사용자에게 요청하고 중단해.

## 4단계 — TC 설계 (Given-When-Then 구조)
분석한 요구사항을 바탕으로 TC 목록을 설계해. 아래 **TC 다양성 필수 요건**을 반드시 지킬 것.

### TC 필드
- **케이스ID**: C-01 형식의 고유 ID
- **기능**: 테스트 대상 기능명
- **구분**: 정상 / 예외 중 하나
- **Given**: 전제 조건 (구체적으로)
- **When**: 사용자 동작 및 입력값
- **Then**: 기대 결과 (모호한 표현 금지)
- **우선순위**: High / Medium / Low

---

### TC 다양성 필수 요건

#### 1. 진입점 다양성 — 같은 기능이 여러 곳에서 동작하면 각각 TC 설계
기능이 A 화면과 B 화면 모두에서 실행 가능하다면, **한 곳에서만 테스트하지 말고 각 진입점마다 TC를 분리**해:
- 기획서에서 동일 기능이 복수의 화면·컴포넌트에 명시된 경우 적용
- 예시 패턴: "목록 화면에서", "상세 화면에서", "모달에서", "인라인으로" 등 진입 방식이 다르면 모두 포함

#### 2. 필터/검색 조합 테스트 — 단일 조건만으로는 불충분
필터·검색 기능이 있으면 아래 시나리오를 **모두 포함**해야 해:
- **단일 조건 선택** (카테고리/옵션별 개별 검증)
- **동일 카테고리 내 다중 선택** (복수 선택 지원 시)
- **서로 다른 카테고리 2개 이상 동시 적용** (카테고리 A + 카테고리 B 조합)
- **필터 + 키워드 검색 동시 적용**
- **필터 + 정렬 조합** (조건 적용 상태에서 정렬 변경)
- **조건 초기화 후 전체 결과 복원 확인**
- **결과 0건 처리** (매칭 항목이 없을 때 빈 상태 UI 검증)

#### 3. 인증/권한 다양성
로그인 방식이나 역할(Role)이 여러 가지인 경우 **각 유형마다 TC를 분리**해:
- 로그인 방식이 N가지면 각 방식의 성공 TC 1개씩
- 공통 예외 시나리오: 잘못된 ID, 잘못된 PW, 필수값 미입력, 중복 로그인
- 권한별로 접근 가능한 메뉴·기능이 다르면 권한별 접근 가능/불가 TC 분리
- 비로그인 상태에서 로그인 필요 기능 접근 시 동작 검증

#### 4. 상태 전환 쌍(Pair) 테스트
ON/OFF, 등록/해제, 활성/비활성처럼 **상태가 반전되는 기능은 양방향 모두 검증**해:
- 상태 A → B 전환 후 결과 확인
- 상태 B → A 복귀 후 원래 상태 복원 확인
- 새로고침 후에도 상태가 유지되는지 확인 (영속성 검증)

#### 5. 데이터 경계값 및 예외 입력
입력 필드가 있는 기능은 정상값 외에 아래를 반드시 포함해:
- **빈 값 제출** — 필수 필드 미입력 시 오류 메시지 표출 여부
- **최대 길이 초과** — 글자 수 제한이 있는 경우 초과 입력 처리
- **특수문자/SQL 인젝션 패턴** — 입력값 이스케이프 처리 여부
- **경계값** — 허용 최솟값, 최댓값, 그 직전/직후 값

#### 6. Assertion 품질 규칙 — 아래 패턴은 사용 금지
```
❌ expect(count).toBeGreaterThanOrEqual(0)   // 항상 참, 검증 의미 없음
❌ expect(true).toBe(true)                   // 아무것도 검증하지 않음
❌ expect(url).toContain('http')             // 너무 광범위
❌ test.skip(true, '추후 구현')              // 미구현 기능은 TC 자체를 만들지 말 것
```
반드시 **구체적인 상태 변화, 건수 증감, 특정 텍스트, URL 패턴**으로 검증할 것:
```
✅ expect(filteredCount).toBeLessThan(totalBefore)   // 필터 적용 후 건수 감소 확인
✅ await expect(page).toHaveURL(/\/detail\/\d+/)      // 상세 페이지 이동 확인
✅ await expect(btn).toHaveClass(/active/)            // 선택 상태 클래스 확인
✅ await expect(toast).toHaveText('저장되었습니다')   // 피드백 메시지 확인
```

#### 7. 기능 유형별 최소 TC 수 기준
| 기능 유형 | 최소 TC 수 | 비고 |
|---|---|---|
| 단순 화면 진입/표출 | 2개 | 정상 진입 1 + 권한 없는 접근 1 |
| 검색/필터 | 8개 이상 | 단일×3, 복합×2, 초기화×1, 빈결과×1, 조합×1 |
| 인증 (방식 N가지) | N+4개 | 방식별 성공×N, 틀린ID×1, 틀린PW×1, 빈값×1, 중복×1 |
| 토글/즐겨찾기/좋아요 | 5개 이상 | 진입점별 등록, 해제, 새로고침 유지, 비로그인, 한도 초과 |
| 정렬/뷰 전환 | 옵션 수 × 2개 | 각 옵션 선택 후 결과 변화 + 선택 상태 UI 반영 |
| 폼 입력/제출 | 4개 이상 | 정상 제출, 필수값 누락, 형식 오류, 중복 제출 |
| 페이지네이션/무한스크롤 | 3개 이상 | 다음 페이지 이동, 마지막 페이지, 이전 페이지 복귀 |

---

설계한 TC 목록을 표 형태로 사용자에게 보여주고 확인을 받아. 수정 요청이 있으면 반영해.

## 5단계 — Notion DB 생성
Notion MCP 도구 `notion-create-database`로 DB를 생성해:
- parent: `.env`의 NOTION_PARENT_PAGE_ID
- title: `[{PROJECT_NAME}] TC 관리`
- properties: 
  - `케이스ID` (title), `기능` (rich_text), `구분` (select: 정상, 예외), `Given` (rich_text), `When` (rich_text), `Then` (rich_text), `우선순위` (select: High, Medium, Low), `통과여부` (checkbox)

생성된 DB ID를 `.notion-db-id` 파일에 저장해.

## 6단계 — TC 업로드
`notion-create-pages` 도구로 설계한 TC를 DB에 등록해. (API 안정성을 위해 한 번에 최대 10개씩 배치 처리해)

## 7단계 — 완료 보고
업로드된 총 TC 수와 Notion DB 링크를 사용자에게 보고해.
